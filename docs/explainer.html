mzera

A small, fast, keyboard-first photo & WebM viewer for Omarchy. This page lays out the requirements, the stack options with an honest comparison, the architecture that makes it fast, how it follows your Omarchy theme, and mockups of the UI. Decisions I need from you are collected at the very end.

1. Requirements

Must have — v1

  • Open a folder recursively; first tiles visible immediately even for ~35 000 files
  • Gallery: flat grid and grouped by folder, thumbnail zoom
  • Format filters: only JPEG, hide WebP, … include/exclude per format
  • Fullscreen viewer: ← → navigate, scale modes, pan/zoom
  • Captions: brief / metadata (path, EXIF) / none. Help overlay with all keys
  • WebM video in the gallery and in the viewer
  • Follows the Omarchy theme automatically
  • Launch: Super+Alt+P, launcher, Nautilus, CLI

Nice to have — later

  • Slideshow, rotate, move to trash, open in editor, copy path
  • Sort by name / date / size, name search, date & size filters
  • Remember per-folder position, mode and filter
  • Hover-scrub on video thumbnails
  • Rust port of the hot modules if profiling ever asks for it

Constraints

  • Wayland · Hyprland · Omarchy; no X11 assumptions
  • Performance is the top priority — test set: 34 981 files, 10 GB, mostly WebP
  • No QtWidgets look; native GTK4/libadwaita is the target
  • English-only UI; no F-keys
  • Deliberately small codebase, "a bit nicer UI with room to grow", not a photo manager
  • Not planned: editing, tags, ratings, library DB, cloud

2. Where the swayimg + Lua approach stops

The current setup (~/.config/swayimg/init.lua, 498 lines, photos wrapper, photos-warm) delivered recursion, filters, three caption modes, a help overlay, scale modes and thumbnail zoom. It is a good fallback and stays. But every remaining requirement hits a hard wall in swayimg itself:

Requirementswayimg realityVerdict
Gallery grouped by folderThe image list is one flat array; the gallery renderer draws a plain grid with no headers or sections. Lua can reorder items but cannot draw anything.impossible
Fast gallery on 35 k filesThumbnails are built by a single background worker; measured: preload stopped after 91 thumbnails and went idle. The 2.5 GB PNG cache we pre-built helps the second visit only.ceiling
WebM videoNo video decoding at all; would need ffmpeg wired into a C codebase.no
"Beautiful UI", clickable filters, chips, popoversOnly a text overlay with a background box. No widgets, no mouse targets.no
Theme syncColors can be set from Lua, and a .tpl could regenerate the Lua file. Works, but only for colors.partial

C · GTK4 + libadwaita in Python — recommended

  • Every hot path is already native: glycin decodes in sandboxed loader processes (no Python GIL involved), libvips is multithreaded C, GTK renders on the GPU, GStreamer plays video.
  • Python only orchestrates: scanning, queues, models, widgets. Scanning 35 k entries with os.scandir is ~0.3 s.
  • GtkGridView recycles tile widgets, so 35 k items cost only as many widgets as fit on screen.
  • Sections by folder, incremental filtering, file dialogs, portals, drag & drop: all built in.
  • Nothing to install. Fastest path to something you can use this week.

Why not the others

  • A — ceiling reached (section 2).
  • B — you would be writing a UI toolkit; video would mean embedding ffmpeg by hand.
  • D — the "right" GNOME answer for a long-lived project, but 2–3× the time and a toolchain to install. Kept as the upgrade path per module.
  • E — QML is not the ugly QtWidgets look; it is what the Omarchy bar is made of. But you said no Qt, and it would be the only Qt app among GTK ones.
  • F — a browser to show a grid of images; heavy, and thumbnails still need a native backend.
  • G — the earlier "option 2": the viewer half can never do video or sections.

4. Recommendation in one paragraph

Build mzera as a GTK4 + libadwaita application in Python, with the module boundaries drawn so that the scanner and the thumbnail service can be swapped for Rust later without touching the UI. Reuse the freedesktop thumbnail cache so Nautilus and mzera share thumbnails. Keep the swayimg config as a fallback command; Super+Alt+P starts pointing at mzera from phase 0.

5. Architecture

native code, off the UI threadPython orchestration
Entry pointscli · desktop entry · Hyprland bind · Nautilus script mzera [--warm] [--gallery|--viewer] [paths…] → single-instance Adw.Application; a second launch just opens more paths.
Scannerthread os.scandir recursive, streams batches of ~500 into the model. Skips hidden dirs. Sorts numerically (1, 2, 10) like today.
ModelGio.ListStore MediaItem: path, folder, kind (image/video), ext, size, mtime. ~1 KB each → ~35 MB for the test set.
PipelineGTK list models FilterListModel (format chips, incremental) → SortListModel → section model keyed by folder. All lazy, no copies.
GalleryGtk.GridView Recycled tiles, header factory for folder sections, jump list, zoom = change tile size. Flat and grouped are the same view with sections on/off.
ThumbServicelibvips · glycin · ffmpegthumbnailer freedesktop cache (~/.cache/thumbnails/large|x-large), worker pool = cores, LIFO priority by visibility, cancel on scroll-away.
Decoderglycin loader processes JPEG, PNG, WebP, GIF, HEIC/AVIF, JXL, SVG, TIFF… decoded sandboxed, off-process, async. EXIF from glycin metadata.
VideoGtk.Video · GStreamer WebM (VP8/VP9/AV1) via gst-plugins-good/bad, VA-API hardware decode on the AMD iGPU.
ViewerGtk.Picture Preload ring ±2, Gdk.Texture LRU with a memory cap, scale modes, pan/zoom gestures, captions & help overlays.
ThemeGio.FileMonitor Reads ~/.local/state/omarchy/current/theme/colors.toml → generates CSS → Gtk.CssProvider. Reloads live on theme change. Optional user override via ~/.config/omarchy/themed/mzera.css.tpl. mode drives Adw.StyleManager dark/light.

6. Performance plan

Test set: ~/Downloads/University_of_Problems — 34 981 files, 10 GB, mostly WebP. Budgets are gates: a phase is not done until its numbers hold on this set.

MetricBudgetHow it is met
Open folder → first grid frame< 300 msScanner streams into the model; the grid shows the first batch while the rest is still scanning.
Full scan of 35 k entries< 1 sos.scandir with DirEntry.stat, no per-file Python objects until batch insert.
Scroll with warm cache60 fpsThumbnails are PNGs read + turned into Gdk.Texture on workers; the UI thread only swaps a paintable. GridView recycles widgets.
Scroll with cold cachevisible tiles first, no jankLIFO priority queue: the tile that scrolled into view last is decoded first; tiles that scrolled away are cancelled.
Cold cache build, 35 k WebP → 256 px≈ 2–3 min on 16 threadslibvips shrink-on-load: libwebp scales while decoding, never a full-size bitmap. HEIF/JXL via libvips loaders, everything else via glycin. Background, nice/ionice.
Viewer next / prev< 50 ms perceivedPreload ring ±2 via glycin async; the texture is ready before the key is pressed.
Filter change on 35 k itemsUI stays responsiveGtk.FilterListModel in incremental mode processes in idle slices.
Memorymodel ≈ 35 MB · textures ≤ 512 MBTile textures are small; viewer textures live in an LRU with a byte cap.

Why the freedesktop cache

  • Nautilus already writes the same files: thumbnails made by one app are reused by the other.
  • Standard: 256 px "large", 512 px "x-large", PNG with Thumb::MTime, invalidated by mtime.
  • Survives restarts; no private format to maintain (the swayimg cache was a private layout with inode keys).

Fallbacks and guards

  • Any decode error → placeholder tile with a format badge, never a crash or a stall.
  • Thumbnail work is cancellable; closing the window drains the pool immediately.
  • mzera --warm ~/Pictures pre-builds the cache from a terminal or a hook, same code path.

7. Theme sync with Omarchy

Omarchy writes the active palette to ~/.local/state/omarchy/current/theme/colors.toml on every omarchy theme set. mzera reads it directly, so it works on a fresh install with zero setup, and watches the file to re-skin itself live. Use the theme buttons at the top of this page to see what that looks like across the mockups.

# colors.toml (Osaka Jade, your current theme)   →   what mzera does with it
mode        = "dark"       →  Adw.StyleManager: dark / light
background  = "#111c18"    →  window, popovers, cards
dark_background = "#0c1512"→  gallery background
lighter_background         →  tiles, chips, section lines
accent      = "#509475"    →  selection ring, active chips, progress
foreground / muted         →  text / secondary text
red · green · yellow       →  errors, video badge, warnings
# optional override, rendered by Omarchy on theme change:
# ~/.config/omarchy/themed/mzera.css.tpl
window.mzera   { background: {{ background }};
                 color: {{ foreground }}; }
.mzera-gallery { background: {{ dark_background }}; }
.tile:selected { outline: 3px solid {{ accent }}; }
.chip.on       { background: {{ mix accent background 25% }}; }

# → ~/.local/state/omarchy/current/theme/mzera.css
# loaded if present, else the same CSS is generated
# in-app from colors.toml

Font: overlays and metadata use the Omarchy monospace font (omarchy font current → JetBrainsMono Nerd Font); UI text follows GTK settings. Light themes (Rosé Pine, Flexoki) switch the whole app to light mode; the viewer background stays black in "clean" mode because photos look right on black — configurable.

10. Roadmap

Phase 0 · ½ day
skeleton
Package layout, mzera CLI, desktop entry, Super+Alt+P → mzera, folder picker, empty window, theme sync live.
Gate: opens from all launch paths, is themed, re-skins when you run omarchy theme set.
Phase 1 · 1 day
gallery + thumbnails
Scanner, model, flat GridView, ThumbService with fd.o cache, --warm, thumbnail zoom, status line.
Gate: 35 k folder → first frame < 300 ms; smooth scroll with warm cache; cold build finishes in the background.
Phase 2 · ½–1 day
viewer
Fullscreen viewer, arrows, scale modes, pan/zoom, preload ring, captions (3 modes), help overlay, key table.
Gate: next/prev < 50 ms perceived on the test set.
Phase 3 · ½ day
filters + folders
Format chips with counts, incremental filtering, sections by folder, jump list, m / [ ].
Gate: toggling a filter on 35 k items never freezes the UI.
Phase 4 · ½ day
video
Install gst-plugins-good/bad + gst-plugin-va, video tiles via ffmpegthumbnailer, inline playback, video in filters.
Gate: WebM plays with hardware decode, arrow keys still navigate.
Phase 5 · ½ day
integration
xdg-mime default, Nautilus "Open with" + script, slideshow, trash, rotate, settings file, swayimg kept as photos --engine swayimg fallback.
Gate: double-click a photo in Nautilus → mzera with the whole folder.

Total to a usable v1: about 3–4 working days. Every phase leaves something you can use.

11. Decisions for you

1. Python now, or Rust from day one?
Recommendation: Python. All hot paths are native anyway; Rust doubles the time and needs a toolchain. The module split keeps a later port cheap.
2. App shell: V1 immersive, V2 classic header bar + sidebar, or V1 with V3 folder browser as a third mode?
Recommendation: V1 now, V3 as a mode later if you miss a folder tree.
3. Thumbnail cache: shared freedesktop cache or a private one?
Recommendation: shared. Nautilus contributes, standard format, nothing to invent.
4. Metadata: side panel (mockup 8.4) or corner overlay like in swayimg today?
Recommendation: side panel; overlay is one more mode if you want both.
5. Keep swayimg + photos as a fallback command after mzera is stable?
Recommendation: keep until phase 5 is done, then decide.
