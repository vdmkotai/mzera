mzera

A small, fast photo & WebM viewer for Omarchy, fully usable from the keyboard and fully usable from the mouse. Decided: Rust (gtk4-rs + libadwaita). This page holds the requirements, the stack comparison, the architecture, the performance plan with measured numbers, the theme sync, the input model and the UI mockups. The plan was verified by four independent checks before any code; what they changed is in section 4b.

1. Requirements

Must have — v1

  • Open a folder recursively; first tiles visible immediately even for ~35 000 files
  • Gallery: flat grid and grouped by folder, thumbnail zoom
  • Format filters: only JPEG, hide WebP, … include/exclude per format
  • Fullscreen viewer: ← → navigate, scale modes, pan/zoom
  • Captions: brief / metadata (path, EXIF) / none. Help overlay with all keys
  • WebM video in the gallery and in the viewer
  • Full keyboard navigation and full mouse navigation, each complete on its own
  • Follows the Omarchy theme automatically
  • Launch: Super+Alt+P, launcher, Nautilus, CLI

Nice to have — later

  • Slideshow, rotate, move to trash, open in editor, copy path
  • Sort by name / date / size, name search, date & size filters
  • Remember per-folder position, mode and filter
  • Hover-scrub on video thumbnails
  • Rust port of the hot modules if profiling ever asks for it

Constraints

  • Wayland · Hyprland · Omarchy; no X11 assumptions
  • Performance is the top priority — test set: 34 988 images (32 779 WebP, all 1920×1080) + 432 WebM
  • No QtWidgets look; native GTK4/libadwaita is the target
  • English-only UI; no F-keys
  • Deliberately small codebase, "a bit nicer UI with room to grow", not a photo manager
  • Not planned: editing, tags, ratings, library DB, cloud

2. Where the swayimg + Lua approach stops

The current setup (~/.config/swayimg/init.lua, 498 lines, photos wrapper, photos-warm) delivered recursion, filters, three caption modes, a help overlay, scale modes and thumbnail zoom. It is a good fallback and stays. But every remaining requirement hits a hard wall in swayimg itself:

D · GTK4 + libadwaita in Rust — chosen, verified

  • Same native libraries as Python for decoding, GPU rendering and video, but everything between them is native too: the model, the filter, the custom gallery widget, the scanner. No GIL, no GC pauses, no FFI trips per tile.
  • Verification found that the gallery must be a custom widget (GtkGridView has no sections). That is 700–900 lines of hot-path code that runs per frame; Rust is the right language for it.
  • Compiles today: gtk4 0.11 (v4_22), libadwaita 0.9 (v1_9), glycin 3.1. Clean build 49 s, incremental 3 s, 160 crates. One 5 MB binary, no Python-version dependency.
  • Cold start measured on a skeleton with 35 000 items already in the model: 160–180 ms to first frame, before any optimisation.

Why not the others

  • A — ceiling reached (section 2).
  • B — you would be writing a UI toolkit; video would mean embedding ffmpeg by hand.
  • C — the earlier recommendation; optimised for "usable in two days". Slower start, 100+ MB model, Python on the snapshot path of a custom widget. Rejected once performance was set as the top criterion.
  • E — QML is not the QtWidgets look; it is what the Omarchy bar is made of. But it would be the only Qt app among GTK ones.
  • F — a browser to show a grid of images; heavy, and thumbnails still need a native backend.
  • G — the earlier "option 2": the viewer half can never do video or sections.

4. Decision

Build mzera in Rust with gtk4-rs and libadwaita. The gallery and the image view are custom widgets that draw textures directly; the model is plain vectors; thumbnails are made by libvips in-process into the shared freedesktop cache; glycin (with a process pool) decodes for the viewer; GTK's built-in GStreamer backend plays WebM. The Omarchy theme is read from colors.toml and reloaded live. Super+Alt+P points at mzera from phase 0; the swayimg config stays as a fallback.

4b. What verification changed

Four independent checks ran against the first version of this plan: a compile + cold-start test of the Rust stack, a thumbnail benchmark on your real folder, a review of GTK 4.22 internals against the gallery/viewer design, and a full input-model design checked against your Hyprland binds. Full reports are in docs/verification/. These are the corrections:

1
GtkGridView has no sections or header factory in GTK 4.22. Only ListView has it; the plan's "GridView sections since 4.12" was wrong. Fix: a custom GalleryView widget with its own layout and snapshot(). Sticky headers, rubber-band and selection rings are drawn, not widgets. It is also the fastest option: zero child widgets, bind cost zero, exact visibility priority, one render pass of 200–400 texture nodes.
2
glycin does not downscale while decoding, and without a pool it spawns a sandbox per image. Fix: thumbnails via libvips in-process (12 ms per 1080p WebP vs 32 ms pure-Rust vs 56 ms via the CLI). glycin with a shared pool is the viewer's decoder and the fallback for HEIC/AVIF/JXL/SVG.
3
gdk-pixbuf has no native loaders on this system. It delegates to a sandboxed glycin process: 6.4 ms per tile and no parallel scaling. Fix: tiles are read with gdk::Texture::from_filename (GTK's built-in PNG decoder, 0.46 ms) or an in-process PNG decode (0.27 ms). Never gdk-pixbuf, never glycin, never WebP as a cache format (6 ms reads).
4
GTK list models hurt at 35 k. SortListModel restarts on every insert during a streaming scan; FilterListModel's incremental mode adds a second of churn. Fix: the scanner emits entries already in sorted DFS order; the model is a vector plus a section-start array plus a filtered index rebuilt in ~2 ms.
5
No stat during the scan. read_dir + d_type only; size and mtime are read lazily by the thumbnail worker and the metadata caption. 35 k entries walk in 50–150 ms.
6
Texture uploads must be throttled. A fresh screen of tiles is ~40 MB of GPU upload; assigning it in one frame stalls. Fix: at most ~32 new textures per frame, nearest to the viewport first; no decode requests while scroll velocity is high.
7
Video packages: gst-plugins-good, gst-plugin-va, gst-plugin-dav1d (AV1 is not in gst-plugins-bad on Arch). GTK's built-in GStreamer sink supports DMABuf zero-copy on Wayland.
8
Test set corrected: ~/Downloads/University_of_Problems-1.9.0-Extended-pc: 34 988 images (32 779 WebP, all 1920×1080, none animated; 1 261 PNG; 948 JPEG) and 432 WebM.
9
Keys the app can never receive: every Super combo, Alt+Tab, Print, media keys, and Ctrl+Space (your keyboard-layout toggle). The input model avoids all of them. Mouse side buttons arrive in GTK as buttons 8 and 9 (verified in GTK's Wayland code).

Why the freedesktop cache still wins

  • Nautilus writes the same PNGs; thumbnails made by one app are reused by the other.
  • 0.46 ms per tile read is already far under budget; a private JPEG cache (0.10 ms, 11 KB) stays as a fallback only if a cold box ever shows PNG decode on the profile.
  • Standard: 256 px "large", 512 px "x-large" for big tiles, Thumb::MTime validation with one statx in the worker.

Guards

  • Any decode error → placeholder with a format badge plus an fd.o fail/ marker so it is not retried.
  • Every request carries a generation number; closing the window or changing the folder drains the pool instantly.
  • Key repeat from the compositor is 40 Hz: the viewer decodes only the latest requested index and cancels the rest.
  • GSK_RENDERER=ngl fallback in the launcher if the Vulkan renderer misbehaves.

7. Theme sync with Omarchy

Omarchy writes the active palette to ~/.local/state/omarchy/current/theme/colors.toml on every omarchy theme set. mzera reads it directly, so it works on a fresh install with zero setup, and watches the file with inotify to re-skin itself live. Use the theme buttons at the top of this page to see what that looks like across the mockups.

11. Decisions for you

1. App shell: V1 immersive (floating pill, no header bar), V2 classic header bar + sidebar, or V1 with the V3 folder browser as a third mode?
Recommendation: V1 now, V3 as a mode later if you miss a folder tree.
2. Thumbnail cache: shared freedesktop PNG cache or a private JPEG cache?
Recommendation: shared. 0.46 ms reads are far under budget and Nautilus contributes thumbnails.
3. Metadata: side panel (mockup 8.4) or corner overlay like in swayimg today?
Recommendation: side panel; the overlay can be an extra caption mode.
4. Keep swayimg + photos as a fallback command until phase 6 is done?
Recommendation: keep, then decide.
